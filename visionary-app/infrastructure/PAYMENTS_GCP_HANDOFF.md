# Payment hosting handoff

D-069, 15 October 2026. The product is local today. The founder plans GCP hosting later; this document describes the configuration handoff for the implemented **test** billing runtime. No project, domain, deployment, Scheduler job or remote webhook is created by this change. The authoritative behavior and remaining live-payment work are in [PAYMENTS_CONTRACT.md](../integration/PAYMENTS_CONTRACT.md).

## One product origin

Serve the built frontend and route `/api/auth/**` and `/api/billing/**` to the standalone connected backend on the same HTTPS product origin. Keep SPA fallback after API routing. A GCP load balancer or reviewed Firebase Hosting rewrite can provide this topology. Browser API paths already remain relative, so the eventual domain does not require a payment-flow rewrite.

Set `AUTH_PUBLIC_ORIGIN=https://<product-domain>` exactly, without a trailing slash. HTTPS activates existing Secure, HttpOnly `__Host-` session/device cookies. Retain exact-Origin/CSRF/expected-account checks and `Cache-Control: no-store`; never cache account, checkout, webhook or invoice responses at the CDN. Preserve raw webhook bytes, `X-Razorpay-Signature`, `X-Razorpay-Event-Id` and the 256 KB webhook limit through the ingress. Forward normal cookies and request headers. Match the Razorpay/Firebase CSP origins in `frontend/vite.config.js`; Vite's development proxy is not a production ingress.

The runtime is built using the backend package and starts with `node dist/src/main-auth.js` from `backend/upstream/backend`. It now listens on `0.0.0.0:$PORT` when the managed environment supplies `PORT`; local `AUTH_PORT` still defaults to loopback port 3001. This follows the [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract#port). Do not start the imported legacy main app for this integration.

## Configuration and identity

Supply `NODE_ENV=production`, the exact public origin, the existing `FIREBASE_PROJECT_ID`, `FIREBASE_PROJECT_KIND` and **existing named** `FIRESTORE_DATABASE_ID`. Verify the database name against the current environment; the example's default is not authority to change databases. Use a dedicated runtime service account with reviewed Firebase Admin/Firestore access through Application Default Credentials. Do not upload the desktop service-account file, CSV or local `.env` into an image. Configure Firebase's authorized domain and browser build settings through the existing auth deployment handoff.

Put Razorpay key secret, webhook secret and a separate random 32-byte lowercase-hex `BILLING_RECONCILE_TOKEN` in Secret Manager. Mount/map reviewed secret versions into backend environment variables; the backend uses environment configuration. Keep key ID and the four existing test plan IDs consistent with that merchant. [The template](../backend/.env.razorpay.example) lists all names. The test-plan setup command is an explicit provisioning task, not a startup action. Reuse its four provisioned plans; restarting or scaling the server must never create plans/subscriptions automatically. Cloud Run provides [Secret Manager integration](https://docs.cloud.google.com/run/docs/configuring/services/secrets).

`BILLING_MODE=test` and `rzp_test_` remain required even with production hosting. Live credentials fail closed. Hosting this code does not enable live billing, tax invoices, production usage enforcement or migration of test financial records into a live ledger.

## Durable reconciliation on Cloud Run

Cloud Run's request-based CPU allocation is unsuitable for relying on an in-process timer between requests; see [billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings). The runtime detects Cloud Run's `K_SERVICE` and disables its local background timer. Configure Cloud Scheduler to POST once per minute to `https://<product-domain>/api/billing/jobs/reconcile`, with header `X-Visionary-Billing-Job` containing the independent configured token. Use HTTPS, restrict access to Scheduler configuration, and exclude that header from request logging. This job credential grants reconciliation only; browser session cookies/CSRF do not grant job access. Missing/wrong token returns 403. Where the selected topology supports a private Cloud Run target, additionally use Scheduler OIDC and service-account invocation IAM; public provider webhook access still needs its own reviewed route. [Scheduler HTTP authentication](https://docs.cloud.google.com/scheduler/docs/http-target-auth) documents those deployment options.

Configure a 300-second service request timeout and a 300-second Scheduler attempt deadline initially, with bounded retries/backoff. Reconciliation starts at most 20 due records, stops beginning another account after roughly 45 seconds, and checks its per-account 120-second provider-work budget between calls. Each provider call has a 12-second timeout. These are work budgets, not a guarantee on a stalled database operation. An interrupted attempt retains its durable due time/three-minute lease and can be retried. A scheduled request reports 503 on storage/provider work failure so monitoring/retries see the problem; local timer failures do not take auth offline. Scheduler can deliver more than once, so Firestore leases coordinate overlapping workers rather than assuming single delivery. Review backlog age and provider rate limits before raising traffic; this bounded scanner is an initial test-volume mechanism. [Scheduler management](https://docs.cloud.google.com/scheduler/docs/creating) describes retry/deadline configuration.

## Register provider delivery after a domain exists

Create a **test-mode** Razorpay webhook for `https://<product-domain>/api/billing/webhooks/razorpay` using the same dedicated webhook secret configured on the backend. Enable the available subscription lifecycle/charge, paid invoice, payment/refund and dispute notifications needed for reconciliation. Confirm exact event availability in the merchant dashboard. The receiver validates signatures and reconciles authoritative provider state, including out-of-order and duplicate notifications. The public URL cannot be registered or verified before a real ingress exists; local configuration does not automatically register it.

After deployment, verify an anonymous account request is denied, authenticated HTTPS cookies/auth-return are correct, a real Razorpay **sandbox** checkout produces a server-verified period/invoice, a second signed-in device reads the same state, and actual signed webhook delivery returns success. Repeat a notification and confirm no duplicate entitlement/charge. Verify Scheduler wakes a zero-instance service, a missing job token is denied, and renewal/cancellation/refund reconciliation persists across a fresh instance. Keep production-money release separate from these hosted sandbox checks.
