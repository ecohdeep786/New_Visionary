# Budget product deployment

The founder's 19 October 2026 direction is a small deployment before there are public users. `budget-profile.json` fixes the initial shape: one Cloud Run service in the existing Firestore region (asia-south1), one vCPU, 512 MiB, request-based CPU, zero minimum and one maximum instance, concurrency 20 and a 30-second request limit. Frontend and API share its managed HTTPS origin. No load balancer, VM, SQL, Redis or model-serving resource is provisioned by this setup. Scale-to-zero can introduce cold starts. Maximum instances are a concurrency limit, not a hard spending cap; build/storage/network and Firebase use can still be billable.

1. Finish code, regression/browser checks and independent exact-SHA review. Package that exact commit with `node scripts/package-product.mjs COMMIT_SHA`. The Git-only archive excludes local environments, dependencies, research captures and user data, and records its SHA-256. Never upload a checkout or service-account JSON.
2. Transfer the exact archive to the authorized project Cloud Shell. Verify its SHA-256 against the local receipt, extract it into a fresh named release directory and enter its product root. Supply only the public Firebase Web SDK values in a separate build JSON; server secrets never belong in frontend arguments or the source archive.
3. `bash infrastructure/gcp/build-reviewed.sh COMMIT_SHA PUBLIC_CONFIG_JSON` builds on the free Cloud Shell Docker environment and pushes a private Artifact Registry image. It creates no Cloud Run service and makes no source/provider/production acceptance claim. Save the immutable registry image digest before deployment.
4. Review the concrete runtime identity, secrets, public front door, Firebase authorized domain and scale limits before applying deployment. A dedicated runtime identity needs the existing application's Firebase Auth and Firestore operations plus access to its specific rate-limit secret; do not give it project Owner/Editor or copy a developer key into the image. Keep test billing explicit and do not enable live money.
5. Deploy the reviewed immutable digest with the budget limits and required production configuration: NODE_ENV, AUTH_PUBLIC_ORIGIN, AUTH_TRUST_PROXY_HOPS=1 for the direct Cloud Run edge, FIREBASE_PROJECT_ID, FIREBASE_AUTH_DOMAIN, the existing named FIRESTORE_DATABASE_ID, and AUTH_RATE_LIMIT_KEY through Secret Manager. Confirm the actual managed HTTPS URL; add that exact host to Firebase authorized domains while retaining existing hosts. Cookie/CSRF origin, Web SDK project/domain and backend project must agree.
6. Verify the deployed HTML/assets/API/cache/CSP/secure-cookie boundaries, login/onboarding/current account and actual coverage/store outcome. Check anonymous/wrong account/CSRF/stale/revoked/outage behavior and reconnect. Keep exact image, service revision, source, environment and observed results. A recipe, API enablement or successful image build is not a deployment acceptance receipt.

The owned domain `visionary.org.in` stays unchanged. A custom app hostname is a later reviewed choice within the budget; this setup does not quietly introduce a fixed-cost load balancer. Main/release promotion and broader curriculum/provider/minor/admission/privacy/payment acceptance stay separate from hosted engineering checks. Revert Cloud Run traffic to the last verified revision for rollback; never delete learner records to undo code.
