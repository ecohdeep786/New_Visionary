# Main-branch production delivery

`visionary.org.in` is served by the existing Mumbai Cloud Run service `visionary-product`. GitHub `main` is the only branch allowed to publish or promote an image. Pull requests to `dev` and `main` run checks without GCP credentials. The workflow pins the image by digest, deploys a no-traffic candidate, probes its exact edge route with a forged forwarding-header sentinel, promotes only while the candidate SHA remains the remote `main` head, and rolls traffic back if canonical smoke checks fail.

The service remains scale-to-zero with maximum one instance, one CPU, 512 MiB, request CPU, no startup boost, concurrency 20 and a 30-second timeout. The global external Application Load Balancer has an estimated base of US$18.25 per 730-hour month, plus metered usage. The current public Cloud Run URL works as the recovery URL until the first main image succeeds. The first release accepts only the currently running, bounded KAN-29 revision as a temporary legacy baseline; if the new candidate fails before promotion, the release restores that revision's original public ingress and records the failure. After a successful main release, rollback is restricted to compatible, immutable images already reachable from `main`.

## First-time owner setup

The commands below use a signed-in Cloud Shell in project `visionary-fd6d2`, region `asia-south1`. Start with `python3 bootstrap.py plan` and review the output. `apply-edge` creates a reserved IPv4 address, two serverless NEGs/backend services, exact-path candidate routing, managed TLS and HTTP redirect resources. Each backend replaces caller-provided `X-Forwarded-For` with the load balancer's client/server addresses. It does not change DNS or Cloud Run. `apply-identity` enables the required IAM APIs and creates the repository/ref/workflow-restricted Workload Identity Federation identity with only Run deploy, Artifact Registry write and runtime-service-account act-as grants. It creates no service-account key and does not grant access to Firebase secrets or user data.

After those changes are reviewed and applied, copy the printed IPv4 address into a GoDaddy `A` record for the apex (`@`, `visionary.org.in`). Preserve existing MX, TXT, CAA and subdomain records. Wait until the Google-managed certificate for `visionary.org.in` reports `ACTIVE`; the first candidate probe requires valid TLS and the apex resolving to this address. The setup script prints the exact record and never logs in to GoDaddy or writes DNS.

Set the repository Actions variables `GCP_WORKLOAD_IDENTITY_PROVIDER` to the provider resource printed by `apply-identity`, `FIREBASE_WEB_CONFIG` to the public Firebase Web SDK configuration object expected by `build-image.mjs`, and set `PRODUCTION_PUBLISH_ENABLED=true`. Keep `PRODUCTION_DEPLOY_ENABLED=false` until the candidate route, DNS and certificate are ready. Use a `main` push or `workflow_dispatch` on `main` to publish an immutable image without moving Cloud Run traffic. Enable `PRODUCTION_DEPLOY_ENABLED=true` only for the intended public cutover; subsequent successful pushes to `main` publish and deploy automatically. A stale run refuses to deploy if a newer commit reached `main`.

## Recovery and evidence

The deployment artifact records the source commit, image digest, candidate/previous revision and whether the previous revision was the one-time legacy baseline. For a failed new candidate, automatic recovery returns traffic to the known previous revision. The one-time legacy path also restores public ingress so the existing `run.app` recovery URL continues to serve. After the first main release, recovery uses the previous verified main revision and leaves ingress restricted to the load balancer.

Check GitHub Actions artifact `main-release-<sha>-<run>-<attempt>` and test logs before diagnosing a release. Confirm `X-Visionary-Revision` on the canonical health/API/static responses and verify anonymous account APIs remain unauthorized. The health-only canary response reports only whether its deliberate forwarded-IP sentinel was removed; it never returns an address. Do not treat a passing health check as acceptance of KAN-29's open real-source coverage, provider, privacy, billing-live, load or full-product launch gates.

Resource lifecycle and cost reference: [Google Cloud global forwarding-rule pricing](https://cloud.google.com/vpc/network-pricing), [custom request headers](https://docs.cloud.google.com/load-balancing/docs/https/custom-headers-global), [forwarding-header behavior](https://docs.cloud.google.com/load-balancing/docs/https). DNS provider: GoDaddy. Production project and domain changes require a recorded change receipt.
