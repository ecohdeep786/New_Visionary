# VATS ownership and pedagogy contract v1

D-087 · 16 October 2026. [Seven-layer implementation plan](../docs/architecture/VATS_IMPLEMENTATION.md) · [policy source](../ml/vats/pedagogy.py) · [backend binding](../backend/upstream/backend/src/learning/pedagogy-proposal.ts) · [shared fixtures](contracts/fixtures/vats-pedagogy.v1.json).

This is an offline library contract, **not a deployed HTTP endpoint or a signed authorization token**. Preserve current Firebase UID/account/test billing and role/source/privacy behavior. Private service IAM/audience/deadline, SQL commands/outbox and frontend integration remain open. No raw browser or provider payload may be treated as this trusted snapshot.

The server prepares `vats-pedagogy.v1`: requestId; scope with UID/workspace/session/requested concept/source/criteria/graph/policy versions and learner/loop revisions; bounded acyclic concept graph; knowledge estimates with assessed counts; current loop phase/failed-check bound/previous and allowed strategies; reviewed error hypothesis, first-encounter/approved-visual flags and hints-only policy. No name, email, billing details, raw chat, protected answer key or hidden reasoning is needed. Revisions are nonnegative JS-safe integers. Maximum 512 graph nodes and 32 prerequisites per node are local defensive contract limits, not tested product capacity. A larger graph needs a reviewed bounded snapshot protocol rather than silent truncation.

Graph source/version/current permission is checked by the backend before constructing a snapshot. Every prerequisite in the snapshot resolves; duplicate IDs/edges, cycles, malformed probabilities/counts and extra fields are rejected. `pKnown` is a posterior estimate, not a mastery flag. An unassessed prior, including .99, leads to assessment rather than assumed understanding. The ML library never updates it. The backend receipt transaction owns ordering/deduplication, criteria, scoring, projection updates and outbox.

Output repeats exact request/scope binding and returns only action, reason, selected concept, allowed strategy or null, requiresAssessment and answerPolicy. Actions are `teach`, `assess_prior`, `await_response`, `check_complete`, `review`. `check_complete` means the server's existing check already passed; it cannot create a scored receipt or mastery. Review is a user-visible suggestion, not a notification to any teacher/guardian. Error classes are reviewed hypotheses, never diagnoses from latency/edits alone. The reference .35/.5/.75 strategy bands preserve the draft's direction but require educational calibration before release; no 100% ZPD or outcome claim is made.

When a prerequisite is selected, the backend must authorize its current source/criteria and create or resume a separately scoped child teaching checkpoint before returning to the original goal. A proposal cannot relabel an existing check/receipt or borrow the requested concept's visual/answer key for its ancestor. The current visual-availability flag applies only to the requested concept; ancestor visuals require a future per-target approved-manifest contract.

The backend validates strict shape, request ID, UID/session/workspace/source/criteria/graph/policy and learner/loop revisions, allowed graph target and strategy, visual admission, hints-only and current loop phase/bound. This binding check is not proof the provider output, pedagogy or answer is correct. Before delivery/commit the real handler must recheck current consent/source/entitlement, evaluate source citations/typed candidate/safeguarding, protect answers, and atomically apply an eligible command. Transport retries keep command identity; a stale proposal is discarded/recomputed and cannot overwrite committed progress.

L1 parser outputs must not overwrite server authority or infer a verified age/grade/role. Ambiguity asks a short clarification; unsupported voice/photo/language stays explicit. L4 cannot skip required source guard on failure or stream early unvalidated output as final. L5 uses approved typed manifests and accessible text/2D fallback; control events are observed after authorized commit, with no arbitrary generated code/URL execution. L6 receives minimized purpose-scoped facts with provenance and correction controls, with actual durable due dates/reconnect. L7 separates operational evidence, optional feedback, human review, approved evaluation sets, training eligibility and deployment approval. Hashing a UID does not anonymize text; no default training or automatic model promotion is authorized.
