## Defect (T09 research round 2 finding, filed as FAP-88)

During the T09 multi-workspace research pass (one adult account holding a Learner and a Teacher workspace, plus a minor account), every teacher class creation emitted a React duplicate-key warning. Console args + component-stack capture pinned it: the duplicated key was the **new classroom's own UUID** (`031ce964-…`), the stack pointed at **TeacherHome**, URL `/dashboard/classes`. Phase bisect showed the warning appears exactly when the class list renders with one class — not at the empty list, the open modal, or the class detail page. Reproduced **4/4** creation runs at beta `fdfc6a45`.

Root cause: `TeacherHome.handleCreate` optimistically prepends the created class (`setClasses(prev => [created, ...prev])`) and *then* dispatches `visionary:workspace-change`; the create write itself already dispatches that same event (`appClient.notifyChange` on `Classroom.create`), TeacherHome listens to it directly, and `useWorkspace` also bumps its revision on it — so multiple `load()` calls race the append. When a fetch that already contains the new class resolves before the append runs, `prev` already includes the class and one commit renders `[C, C]`. `load()` replaces the whole array, so the visible list self-heals; the duplicate-key render (console noise + possible card flash) is still emitted on every creation.

## 1. The change (one file; both write points idempotent by classroom id)

- `frontend/src/pages/dashboard/role/TeacherHome.jsx`:
  - `handleCreate` no longer blindly prepends: `prev.some(c => c.id === created.id)` — an existing entry is merged in place (`{ ...created, student_count: c.student_count }`, preserving the fetched count), a genuinely new class is still prepended.
  - `load()` dedupes the fetched `ownClasses` by id (`seenClassIds` filter) before `setClasses`, as a defensive guard against any event interleaving or duplicate storage rows; ordering (`-createdAt`) unchanged.

Rendered behavior in the healthy case is byte-identical: same grid, same keys (`key={c.id}`), same stats, same copy.

## 3. Research round 2 results beyond the defect (recorded, not filed)

The same probe round verified the T09 isolation/continuity lanes clean (`research/t09-round2-workspaces.json`, `research/t09-r2-spot.json`, `shots/`):

- **No class leak across the same account's workspaces**: the learner workspace's Classes page shows the honest "No classes yet" + join-by-code empty state while the teacher workspace holds the class (teacher-created Classroom rows carry no owner stamp — isolation is enforced at the service layer via `teacher_email`/`teacher_id` (`ownsClass`) and learner lists read `Enrollment.student_email`; unknown `?class=` deep-link params keep the URL with the honest empty state).
- **No project leak**: the teacher workspace's Build page shows no student project — ArtifactStudio stores projects per workspace inside `visionary_workspace_v2` `db.data` (not the global `visionary_entity_*` store), so isolation is structural.
- **Continuity**: switching Learner → Teacher restores the teacher's saved `lastPath` to the exact class page (`/dashboard/class/<id>`); a full reload restores the active workspace (`db.active` + switcher value) and the session; the ClassDetail learner redirect (`/dashboard/classes?class=<id>`, by design for real enrolled students) replaces the learner workspace's saved lastPath with `/dashboard/classes` — an acceptable continuation trade-off, noted for the record.
- **Minor gating**: a minor account renders **no workspace switcher at all** (no add-role option; `addRole` also rejects non-student roles server-side of the UI), and FAP-87's notice still explains `/dashboard/prepare` for the minor. Observation (not filed): the onboarding wizard offered the minor the "Exam preparation" goal too.
- **Mobile 390**: no horizontal overflow (`scrollWidth 390 == innerWidth 390`), the "Toggle navigation" drawer opens with all 14 dashboard links visible.
