## Defect (T06 responsive audit, filed as FAP-82)

On `/pricing` at 320 CSS px with **200% root text** — the same text-resize simulation the product's own `design-quality-review.mjs` contract uses — the FAQ section rendered **396px wide, +124px past the 320px viewport**, with the page clipping overflow (no horizontal scroll): every FAQ question row cut at the right edge and the disclosure chevrons unreachable, so the accordion could not be read or operated. The FAQ h2 computed **80px** (`--fs-display` 2.5rem at the phone ladder); its longest word alone needed 396px, and the grid track (`min-width: auto`) expanded past the viewport, dragging all six question buttons. The billing toggle clipped +35px.

Root cause: the public display type ladder set phone (≤734px) and tablet (≤1068px) scale tokens as **fixed rem** values — `--fs-display/--fs-h2/--fs-product-section` (2.5rem/3.5rem), `--fs-hero-headline`/`--fs-category-statement` (2.75rem/4rem) — and the same ladder existed in two more places outside the token system: the **unified h1 role law** in `apple-typography.css` hardcoded `2.75rem/4rem/5rem !important`, and `--fs-hero-eyebrow` (2.5rem) drove the home hero's "One intelligence" prefix line. At 200% root text those rem values double while the viewport stays 320–430px, so display headings exceed the viewport and `min-width: auto` grid items drag whole sections past the clipped page edge. Desktop tokens were viewport-aware (clamp with vw); the phone/tablet ladder dropped that awareness.

Measured at beta `35b77791`, 12 routes flagged h1/h2 offscreen at 320/200%: `/` (+63), `/student` (+38), `/teacher` (+41), `/parent` (+57), `/professional` (+24), `/organization` (+20), `/help` (+39), `/pricing` (+124, FAQ controls), `/research` (+183), `/careers` (+69), plus `/about` (+296) and `/partners` (+102) whose instances also include a second mechanism (min-content grid tracks). At 390/200% the same routes flagged with smaller offsets. Zero console errors; zero document overflow at 100% text.

[Apple HIG — Layout](https://developer.apple.com/design/human-interface-guidelines/layout): "Design a layout that adapts gracefully and consistently … to text-size changes." The product must remain usable when text scales, not merely non-overflowing at default text.

[WCAG 1.4.4 (Resize Text)](https://www.w3.org/TR/WCAG22/#resize-text): no loss of content or functionality at 200% text.

## 2. The change (three source files + enforcement)

- `frontend/src/styles/rhythm.css`: every display-scale token in the phone/tablet ladder now carries a viewport cap `min(<rem step>, <vw>)` — `--fs-display`, `--fs-product-section`, `--fs-h2` at `min(<step>, 13vw)`; `--fs-hero-headline`, `--fs-category-statement`, `--fs-hero-eyebrow` at `min(<step>, 14vw)/min(<step>, 13vw)` — across all four ladder blocks (:root ≤1068, :root ≤734, section ≤1068, section ≤734; 15 token lines). The rem step keeps the accepted Apple ladder at default text (the vw side never binds at any supported width: 13vw ≥ 40px at 320; 14vw ≥ 44px at 320); the vw side keeps 200% text inside the viewport. FAP-82 law comment added.
- `frontend/src/styles/apple-typography.css`: the unified h1 role law's three hardcoded steps (base 2.75rem, ≥640px 4rem, ≥1280px 5rem, all `!important`) now carry `min(<step>, 14vw)` — the same 44/64/80 ladder with the same cap; each cap never binds on its band's smallest width (44.8 ≥ 44 at 320, 89.6 ≥ 64 at 640, 179.2 ≥ 80 at 1280).
- `frontend/src/pages/landing/AILearningPage.jsx`: the pricing FAQ grid declares a fail-closed base column `grid-cols-[minmax(0,1fr)]` (keeping the accepted lg two-track form), and the billing toggle's phone padding is viewport-aware `px-[min(1rem,5vw)]` (keeping `sm:px-5`). 5vw at 320px = 16px = the rem step, so default text is unchanged.
- No copy, flow, data or workspace change. All desktop (≥1069px) tokens untouched.

## 7. Reference basis (Apple resources, 2026-11-11)

[Apple HIG — Layout](https://developer.apple.com/design/human-interface-guidelines/layout): adapt gracefully to text-size changes; primary content areas should be legible without horizontal scrolling.
