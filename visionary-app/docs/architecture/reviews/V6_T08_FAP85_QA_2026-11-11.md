## Defect (T08 audit finding, filed as FAP-85)

At beta `a0aeb95b`, `/forgot-password`'s **preview** success view claimed **"Check your email — If an account exists for \<email\>, you'll receive a password reset link shortly"** although preview mode has no email transport. Worse, `ForgotPassword.jsx` **discarded the `resetToken`** that `appClient.js resetPasswordRequest` returns (`{ ok: true, resetToken }` — a single-use token, 15-minute TTL, stored in `visionary_reset_tokens`), and `/reset-password` requires `?token=` (or `?oobCode=`) — so the created token was unreachable and **preview users had no password-recovery path at all**: submitting the form left them at a dead end (`/reset-password` without a token shows the honest "Request a new reset link" invalid state).

Reproduced live at beta (same-context probe): after submitting a known local address, `visionary_reset_tokens` gained a real token (`6baf4c5f…`, ~15 min TTL) while the UI stayed on `/forgot-password` with the false claim — and navigating to `/reset-password?token=<that token>` lands on the working "Set a new password" form, proving the continuation path existed but was never surfaced. The unknown-address case showed the same false claim (the fresh-context probe found no token was created — `resetPasswordRequest` returns `{ok:true}` without a token for unknown addresses).

Why it matters: the same unfulfilled-promise violation as FAP-70 (this time promising an emailed *link*), plus a genuinely broken recovery flow — the token was created and then dropped.

## 2. The change (one source file, preview branch only)

- `frontend/src/pages/ForgotPassword.jsx`: a single `preview = base44.auth.source !== 'firebase'` flag gates (a) the form supportingText, (b) the submit label ("Create reset token" vs "Send reset link"), (c) the success view: preview shows the truthful disclosure and — when the local adapter returned a token — a primary "Continue to reset password" link to `/reset-password?token=${encodeURIComponent(resetToken)}`; unknown addresses get the honest "No local account found" state. The connected Firebase arm keeps its byte-identical success view and `sendPasswordResetEmail` transport; its `auth/user-not-found` anti-enumeration catch is unchanged. The doc header records the FAP-85 law. `ResetPassword.jsx` needed no change (it already reads `?token` and preview verifies via `Promise.resolve('')`).
- No route, flow, data, or workspace change. The token stays single-use with the existing 15-minute TTL (`RESET_TOKEN_TTL_MS`); `resetPassword` already invalidates it after use.

## 3. Contract tests (4 new)

`frontend/tests/fap85-forgot-preview-truth.test.mjs` (4 tests): (1) the preview flag is derived from the auth source and gates the form copy/button while the connected copies are retained; (2) the preview success step discloses the simulation (including the 15-minute lifetime), captures `result?.resetToken` instead of discarding it, and surfaces the `/reset-password?token=` continuation; (3) the connected "Check your email" claim lives only in the connected arm (position check — preview arm has its own truthful title and no token continuation); (4) regression guard: `ResetPassword.jsx` still reads the `?token` param the continuation link sets.
