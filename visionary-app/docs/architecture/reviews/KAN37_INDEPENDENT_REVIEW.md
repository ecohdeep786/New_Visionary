## Required corrections

1. **[P1] Migration identity checks are disconnected from execution.** `migration-runner.ts:60–96` accepts only an arbitrary `appliedBy` string and executes statements without calling the separate identity helpers. No store contract requires an authenticated migration-purpose connection. The actual runner accepts `appliedBy: 'app-runtime'` and applies every migration. Helper-only denial tests do not prove the runner is guarded. Require a validated execution identity/adapter at the command boundary and actual database permissions; test the runner refusing a runtime connection before statements, and verify DML-only runtime versus DDL migration roles in disposable synthetic PostgreSQL. This probe establishes a missing framework guard, not an exploit against a deployed database; no live credentials were used.

2. **[P1] SQL statements and their ledger receipt are not atomic.** `migration-runner.ts:86` executes each statement, then records the receipt at 96. `MigrationStore` has no required transaction/commit/lock operation. A failure after the first successful statement or between SQL completion and receipt persistence replays earlier work on retry; concurrent runners can both select the same pending version. The included probe demonstrates an already completed INSERT executing twice after a later statement fails. Require a documented transaction/lock strategy with durable outcome reconciliation (including steps that cannot run transactionally); test mid-statement, post-SQL/pre-receipt, commit ambiguity, restart and concurrent runners. The existing test only checks final ledger counts and cannot support the claimed no-double-apply guarantee.

3. **[P1] The registry does not mirror the reviewed target SQL.** `migration-registry.ts:16–32` copies only five of DATA-01's ten tables, omits the foreign keys/indexes and consent/share/invitation/audit/tombstone definitions, and writes camelCase identifiers without quotes. PostgreSQL folds those identifiers to lowercase, whereas DATA-01 uses quoted camelCase names. It is a different schema, not a checksummed canonical migration. Version 2 adds revision/dispatchedAt fields that the DATA-01 SQL already declares, then its down path drops them. Consume the single accepted canonical migration artifact and verify a schema diff against Prisma after apply and rollback. Do not maintain a second partial SQL implementation or call deferred adoption an accepted integration result.

4. **[P1] Integrity checking trusts caller-supplied checksums and leaves rollback SQL unprotected.** `migration-runner.ts:24–36` compares stored string fields without recomputing the supplied SQL digest. Changing statements while retaining the old checksum leaves `verify().consistent === true`. `rollbackLast` at 120 skips preflight/drift checks and executes the current `entry.down`; `migrationChecksum` covers only up statements. The probe changes version 2's down SQL to `DROP TABLE persons` after apply and the runner accepts it. Derive/validate an immutable approved artifact containing forward/backward SQL and relevant metadata, verify it against the applied receipt before either direction, and refuse drift before writes. Add tests for changed SQL with stale digest, changed down SQL, renamed/removed versions and invalid prerequisite/version data.

5. **[P1] Backfill work is not bounded at the source/loop boundary.** `backfill-runner.ts:90–102` trusts source row counts and cursor progress in an unbounded loop. Requested batch size 1 still processes a two-row page; a nonterminal empty page with the same cursor repeats indefinitely. The bounded probe stops its source after three requests to avoid a hang; the runner reaches that sentinel instead of detecting no progress. Validate page size and cursor invariants before writes, add cancellation plus explicit time/row/batch budgets, and save resumable state on bounded exit. The mark callback is merely documented as idempotent: test partial-batch replay with a real idempotent store write, not only a Set that hides duplicate calls.

6. **[P1] Durable database, compatibility and rollback acceptance is still missing.** Both provided store implementations are process-local Maps. `InMemoryMigrationStore.exec` records strings and notices CREATE TABLE names; it does not execute ALTER/DROP or enforce SQL constraints/permissions. A history marker proves neither physical schema rollback nor restart durability. The provided synthetic tests are useful unit preparation, but cannot satisfy DATA-02's versioned migration/identity/backfill/compatibility/rollback outcome. Supply a real disposable synthetic PostgreSQL adapter/harness with separate roles, cold restart, actual data/schema checks, backward compatibility and recovery evidence before claiming that scope. No shared or real-user store is needed or authorized.

7. **[P2] Standard verification does not register this suite/build.** The branch adds a focused tsconfig and tests requiring `dist/src/data`, but does not change the root check or CI invocation to compile/run them. A fresh normal check can therefore omit all twelve tests; a direct test invocation before compilation lacks required output. Add the focused build/tests to the relevant standard check/CI path with independent locked dependencies. Fill the handoff's literal `<filled at commit>` candidate field and correct its unsupported guarantees.
