## Main release and load-balancer design

The proposed keyless trust uses numeric repository1357462978 and owner221676162 plus refs/heads/main, consistent with Google's [deployment federation guidance](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines). Use an event_name push condition and the intended workflow identity where available, as main ref alone can also occur in privileged PR-target contexts. Keep PR checks unprivileged, actions pinned to reviewed full commits, deployment token issuance confined to the deployment job, and credentials outside build context/logs/artifacts. CI should have only existing-service deployment, private-repository image write and actAs on the dedicated runtime identity, not project IAM, DNS/Compute changes or secret-value access. Static load balancer/certificate/NEG bootstrap belongs to the authorized owner operation.

Initial concern: setting trustProxy2 while accepting direct public run.app requests creates a shorter path where supplied forwarded values can be mistaken for trusted client IPs. The implementer's revised plan uses internal-and-cloud-load-balancing ingress and validates the actual LB chain before setting2. Direct public run.app access, including old test-tag access on that service, then stops. Record that intentional cutover and do not claim the old direct-host journey remains publicly available.
